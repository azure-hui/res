控制MVP复杂度（小团队3-6个月上线）
匹配中小餐厅成本敏感 + 高峰期性能要求
支持未来从小单店 → 小连锁扩展
优先保护核心价值（实时洞察 + 预测 + 警报）

3. 上下文映射（Context Map）简要关系
采用DDD Context Map 的常见模式（初期简化版）：
实时运营监控 ← Upstream 集成与采集（发布订单/客流事件）
实时运营监控 ← Upstream 订单与菜品分析（消费日/周快照数据）
预测与备货 ← Upstream 订单与菜品分析 + 集成与采集（订阅历史订单 & 实时事件）
顾客洞察 ← Upstream 订单与菜品分析（订阅订单事件，匿名关联）
实时运营监控 → Downstream 身份与通知（触发警报）
总部多店上下文 ← Upstream 所有其他上下文（聚合事件/快照）
关键集成模式建议：
大部分采用 事件驱动（Domain Event） + 最终一致性（避免分布式事务）
少量采用 Conformist 或 Anti-Corruption Layer（如外卖平台数据格式转换）
避免 Shared Kernel（共享模型），除非极小（如User ID格式）
4. 为什么这样划分（与约束/权衡对齐）
成本与性能：核心实时部分（运营监控）保持单体高性能；预测/顾客洞察可异步、低优先级计算，控制云费。
合规：顾客洞察独立，隐私逻辑集中，便于审计和“一键删除”。
易用 & MVP周期：初期聚焦4个Must上下文（实时监控 + 订单分析 + 采集 + 身份通知），快速出价值。
可扩展：多店总部作为后期上下文插入，不破坏单店模型。
团队并行：未来可按上下文分配小团队（1-2人/上下文）。
