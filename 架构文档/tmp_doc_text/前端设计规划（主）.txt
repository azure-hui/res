前端关键文件说明（与后端配合细节）
app/dashboard/page.tsx
渲染实时KPI（营收、翻台、警报）
用 useRealtimeSubscription hook 订阅后端 WebSocket（e.g., /ws/realtime?store_id=xxx）
数据从 TanStack Query 缓存 + Zustand 状态同步
与后端配合：调用 /api/realtime/kpis + 推送事件 from Redis Streams
components/VoiceAssistantButton.tsx
点击录音 → Web Speech API 转文字 → 调用后端 /ai/intent (Tool Calling)
流式显示 LLM 输出（useStream hook）
与后端配合：后端 LangGraph 处理意图 → call create_order Tool → 返回 order_id
components/ApprovalDialog.tsx
高风险操作弹窗（e.g., 调整库存）
调用 /approval/request → 后端存 audit 表 + 推送通知
与后端配合：WebSocket 接收审批结果 → 刷新 UI
lib/api/client.ts
axios.create({ baseURL: backend_url })
拦截器：加 JWT header + refresh token 逻辑 + 429 限流重试
与后端配合：orval 生成类型安全的 API 调用（e.g., api.orders.createOrder(payload)）
总结：前端总体设计原则
移动优先：Tailwind 响应式 + PWA，确保手机/平板操作流畅（语音点单/警报推送）。
实时性：Socket.IO + TanStack Query 最小化轮询，依赖后端 Streams 推送。
安全：前端不存敏感数据，只存 JWT；所有 API 调用带 token + 校验响应 code。
大模型配合：前端只做输入采集/输出渲染，核心逻辑在后端 LangGraph（防泄露）。
开发效率：shadcn 组件 + orval 类型生成，减少前后端对齐时间。
这个前端结构与后端完美对称（dashboard ↔ realtime_monitoring），总代码量控制在5-10k行。

关键技术/工具
WebSocket 高峰连接
多店/多用户同时连接导致服务器连接数爆炸、内存/CPU 压力大、掉线频繁
1. 每门店连接数限制（前端 Zustand 记录已连接门店，超限提示“请切换门店”） 2. 聚合订阅：前端只订阅当前门店 channel（e.g., ws/realtime/${storeId}） 3. hooks 层自动重连 + 指数退避 4. 连接断开时显示“网络不稳，重连中...”
1. Redis Streams 按门店独立 channel + consumer group 2. 后端限流：fastapi-limiter 限制每个 IP/用户/门店的 WebSocket 连接数（e.g., 5/分钟） 3. 连接池管理：uvicorn worker + connection limit
★★★★★
中等（1-2 周）
Socket.IO + Zustand + fastapi-limiter
边缘/语音功能
浏览器语音识别不稳定（噪音、方言）、延迟高、弱网/离线不可用
1. 前端优先 Web Speech API（浏览器原生，零成本） 2. fallback 到 Whisper.js（本地 WASM 版，离线可用） 3. 录音权限弹窗 + 超时自动停止 4. 弱网时本地缓存语音片段，网络恢复后批量上传 5. UI 显示“正在听...” → “识别中...” → “点单成功”
1. /ai/voice-intent 端点接收音频/文本 → LangGraph Tool Calling 2. 边缘上报用 MQTT/WebSocket 轻量通道 3. Redis Streams 暂存离线事件，恢复后回放
